# ADR-20: Request identification, idempotent mutations and optimistic concurrency

Date: 2026-11-07 · Status: Accepted for design — implementation pending · Scope: F-1-S4, all current and future mutation routes.

## Context

ADR-14 requires "idempotency keys for retried commands, optimistic concurrency for updates and RFC 9457 problem details" in the API contract. F-1-S5 implemented reads; F-1-S6 added camera soft-delete. The three current mutation routes — `PUT /grants/{camera_id}`, `DELETE /grants/{camera_id}` and `DELETE /cameras/{camera_id}` — have no request identification, no idempotency guarantee and no concurrency protection:

- A network retry re-executes the mutation. For grant PUT this is safe by SQL upsert semantics but produces no stored response to replay; for DELETE it is a silent no-op indistinguishable from success.
- Two concurrent operators issuing conflicting mutations race with last-writer-wins and no conflict signal.
- Log lines carry no stable correlation identifier, making multi-request troubleshooting dependent on timestamps and request IDs that differ per attempt.

This ADR records the mechanism for all three concerns so that every current and future mutation route follows the same contract.

## Decision

### Request identification (all routes)

- **`Idempotency-Key`** (required, canonical UUID): identifies one logical operation. The client generates it once and reuses it across retries of the same operation; a different operation uses a different key. Liveness and readiness probes accept an optional valid key (they are not mutations). Read routes require a valid key for identification and logging but do not cache or replay responses — idempotency storage applies to mutations only.

- **`X-Correlation-Id`** (optional, canonical UUID): a client-supplied trace identifier that spans service boundaries. When absent, middleware generates one. It is returned in every response header. An invalid supplied value (not a canonical UUID) yields 400. This is distinct from the existing per-attempt `X-Request-Id` generated by the request-ID middleware; both are present on every response.

- **UUID format:** "canonical UUID" means the 8-4-4-4-12 hex string form defined by RFC 4122 / RFC 9562 (lowercase or uppercase hex, hyphens in the standard positions). Any version and variant is accepted. The server does not restrict to a specific version; it validates format only.

- **Logging:** identifiers, method, route template, status and duration are logged for every request. Request bodies are logged only for explicitly approved routes and fields; no body fields are approved yet, so bodies are omitted from logs until a human approves specific fields. Credentials and tokens never appear in logs or stored records.

### Idempotency (mutation routes)

- **Storage:** successful mutation results are stored in a new `idempotency_keys` table (alembic revision 0004). The key is scoped by authenticated tenant and subject only. Method, path and body live in the fingerprint, not the namespace. This means a client that reuses the same UUID for a different operation (different method or path) receives 409 `idempotency_key_reused` rather than silently creating a separate record.

- **Fingerprint:** SHA-256 over the canonical HTTP method, path (including the camera_id segment), sorted JSON request body, and the `If-Match` header value when present. The fingerprint distinguishes "same logical operation" from "different operation reusing a key."

- **Replay:** a retry with the same key and matching fingerprint returns the stored response (status, body, applicable validator metadata) without re-executing the mutation. The response carries the current request ID, not the original one. A retry with the same key but a different fingerprint yields 409 with an RFC 9457 problem detail (`idempotency_key_reused`).

- **Retention:** successful results are retained for one hour. After expiration the key may be reused for a new operation; a retry after expiration re-executes the mutation. Failed mutations (4xx/5xx) are not stored; the client retries with the same key and the request re-executes.

- **Atomicity:** the mutation and its idempotency record commit in the same database transaction. A crash between mutation and record storage is impossible because they share the transaction boundary.

- **Concurrent duplicates:** claim a previously absent key with a unique-key insert within the mutation transaction. A competing insert for the same key waits on the first transaction; after commit, read the record and compare the fingerprint, and after rollback retry the claim. Apply a five-second database lock timeout and map a claim timeout to 409 (`request_in_progress`). Handle expired records atomically under the same per-key serialization.

- **Non-blocking dispatch:** use an asynchronous database call so a lock wait releases the event loop. Each waiter still occupies a database connection. Bound duplicate admission and reserve database capacity for unrelated work; a request denied admission returns `409 request_in_progress`. Exact pool and admission limits must be configured and documented. Tests must hold a claim open, exercise the admission bound, verify timeout and rollback recovery, and prove an unrelated database-backed request completes while waiters are held.

- **Authorization on replay:** authentication and authorization are checked before returning a stored response. Because the key namespace is scoped to (tenant, subject), a different caller has a separate namespace: reusing the same UUID under a different tenant or subject simply finds no record and proceeds as a new request — it does not receive the original caller's stored result. Within the same namespace, the current request's authorization is verified (the caller must still hold the role required by the route) before the replay is returned. A caller whose authorization has been revoked since the original request receives 403, not the stored body.

### Optimistic concurrency (mutation routes)

- **Revision:** the `cameras` table gains an integer `revision` column (default 1). The revision is incremented on every mutation that changes the camera's accessible state: grant PUT (upsert/reactivation), grant DELETE (when a grant row was actually deleted), and camera DELETE (soft-delete of an active camera). The revision is monotonic per camera_id and never resets across delete/recreate cycles. Grant DELETE on an absent grant does not increment (no state change occurred).

- **Resource-specific validators:** use resource-specific strong ETags and standard `If-Match`, confirmed by the human on 2026-11-07. Add admin-only `GET /grants/{camera_id}` returning `GrantResponse` and its ETag; `GET /cameras/{camera_id}` returns `CameraState` and its own ETag. An absent selected resource has no current validator. A grant validator cannot validate the camera target or vice versa.

- **Shared validator generation:** one component produces opaque tags incorporating resource type, identifier, representation version and revision. Clients preserve the tag without interpreting it. The existing shared camera revision is the revision source for camera and grant tags in this slice; their tags differ even at the same revision. Advance it atomically for related state changes. This deliberately permits conservative conflicts across related changes. Other resource families may provide another revision source through the same interface. Every change to the selected representation data or variants must change its strong validator; control serialization and representation versioning accordingly.

- **Conditional requests:** optional `If-Match` uses RFC 9110 section 13.1.1 strong comparison, including tag lists and `*`. Evaluate against the selected representation of the actual target, subject to normal response precedence and matching completed idempotency replay. A false precondition on an operation that would otherwise succeed yields 412 with no writes; this includes an absent grant for which an unconditional DELETE would return 204. An unconditional DELETE of a never-created camera returns 404. Do not infer success of a specific previous request merely from absence; completed idempotency records supply retry evidence. Where authorization permits disclosure, a 412 problem may include the current target ETag when one exists.

- **DELETE response headers:** omit ETags from successful DELETE responses consistently. RFC 9110 section 15.3.5 permits metadata on 204 responses; omission is AVA's chosen contract. Clients use GET to obtain a current validator for a surviving resource. Grant PUT returns its updated grant ETag with the 200 response; it does not return the camera ETag.

- **Replay precedes precondition:** when a completed idempotent replay is found (same key + matching fingerprint), the stored response is returned regardless of the current `If-Match` value in the retry. The original request succeeded at its own revision; re-evaluating the precondition on replay would produce a spurious 412 if state changed after the original commit. The original `If-Match` value is part of the fingerprint, so a retry with a different If-Match is a different logical operation (409).

### Mutation-specific semantics

- **Grant PUT** (`PUT /grants/{camera_id}`): replaces the grant and upserts/reactivates the camera row atomically. Increments camera revision. Returns 200 with `GrantResponse` body and its updated grant ETag.

- **Grant DELETE** (`DELETE /grants/{camera_id}`): hard-deletes the grant row. When applicable preconditions pass, returns 204 whether or not a grant existed — revocation is idempotent; "already revoked" is success. Increments camera revision when a grant row was actually deleted (state changed: the camera's accessible tenant set shrank). Does not increment when no grant existed (no state change).

- **Camera DELETE** (`DELETE /cameras/{camera_id}`): soft-deletes the camera row. Returns 204 (no body) when an active camera was deleted or when it was already soft-deleted (idempotent). Returns 404 when no camera row ever existed. Increments camera revision on a successful (first) deletion; does not increment on the idempotent no-op.

### Architecture placement

Per ADR-16 layering:

- **Presentation** (`api/middleware.py`, `api/routes_events.py`): parses and validates `Idempotency-Key` and `X-Correlation-Id` headers; generates correlation ID when absent; invokes application use cases with parsed values; maps results to responses including ETag.

- **Application** (new `application/mutation.py`): one reusable workflow authorizes, claims the idempotency key, replays or checks target preconditions, executes the operation, advances revisions when state changes, stores the response and commits atomically. Resource handlers supply target lookup and state changes through explicit interfaces. They do not implement separate retry, locking or precondition rules. The application defines the idempotency and transactional contracts; infrastructure implements the transaction.

- **Infrastructure** (`persistence/mutation_postgres.py`, updated `grants_postgres.py`, `cameras_postgres.py`): implements the idempotency key repository and revision-aware SQL. The repository stores and retrieves key/fingerprint/response tuples; it does not make business decisions.

### Migration

Alembic revision 0004 (additive, backward-compatible):

- `idempotency_keys` table: `key_hash` (PK, SHA-256 of namespace+key), `namespace` (tenant:subject), `fingerprint`, `status`, `response_status`, `response_body` (jsonb), validator metadata, `created_at`, `expires_at`.
- `cameras.revision` column: integer, NOT NULL, default 1; backfilled to 1 for all existing rows.

Existing clients that do not send a valid `Idempotency-Key` must be updated. The migration itself is safe: no data loss, no schema break. A deployment window or feature flag may be needed during rollout; this is an operational concern outside the ADR scope.

## Alternatives considered

**Optional idempotency key:** rejected because it leaves the retry-safety gap open for clients that do not opt in. A required key makes the contract uniform and testable; the cost is a one-time client update.

**Server-assigned keys:** rejected because the client must know the key before the first request to reuse it on retry. Client-generated UUIDs are standard (RFC 4122) and require no extra round-trip.

**Timestamp-based concurrency (compare `updated_at`):** rejected because timestamps can collide within the same microsecond and are not monotonic across clock adjustments. An integer revision is unambiguous and cheap to check.

**Revision on the grant row in addition to the camera:** deferred. The camera revision covers all state changes visible to the client: grant PUT changes camera state, grant DELETE (when a grant existed) changes the camera's accessible tenant set, and camera DELETE changes visibility. All three are reflected in the single camera revision. Adding a second revision increases complexity without current benefit. Revisit if a future route mutates grants without touching the camera row or without changing its accessible state.

**Weak ETag (`W/"rev-N"`):** not suitable for strong `If-Match` comparison.

**Shared application revision header:** not selected; resource-specific ETags and standard `If-Match` are the confirmed contract. The underlying revision source may still be shared while each HTTP target has its own validator.

**Namespace including method and path:** rejected. Including method and path in the namespace (rather than only in the fingerprint) would cause a key reused across different operations to create separate records instead of triggering the agreed 409 conflict. The namespace identifies the caller; the fingerprint identifies the operation.

**Synchronous client-side wait for concurrent duplicates:** rejected because it holds a FastAPI worker (or connection pool slot) in a blocking sleep for up to five seconds, which can exhaust capacity under a burst of retries. The asynchronous database operations release the event loop; a server-side `lock_timeout` bounds the lock wait, and admission control protects capacity.

**Storing failed responses for replay:** rejected. A 4xx/5xx response does not represent a completed operation; storing it would prevent legitimate retries after a transient failure. Only successful (2xx) results are stored.

## Consequences

- All API clients must generate and send a canonical UUID `Idempotency-Key` on every request (mutations and reads). Liveness/readiness probes may omit it or send a valid one. Reads receive no replay guarantee.
- The middleware layer grows: key validation, correlation ID generation, and structured logging. Invalid keys are rejected before routing.
- One new database table and one new column; the migration is additive.
- A new application module (`mutation.py`) and a transaction adapter (`mutation_postgres.py`). The existing `access.py` ports are extended with revision-aware signatures but not restructured.
- Add admin-only grant GET and its representation/ETag contract; camera GET also exposes its own ETag.
- OpenAPI document gains: `Idempotency-Key` and `X-Correlation-Id` header parameters, `If-Match` parameter on mutations, validator response headers according to the confirmed design, `X-Correlation-Id` response header, and 409/412 problem-detail responses.
- The connection pool must be sized to tolerate a bounded burst of duplicate waiters (each holding a connection for up to five seconds during the lock wait). This is an operational sizing concern validated by the concurrent unrelated-request integration test.
- Tests must cover: replay, key reuse with different fingerprint (409), expiration, concurrent duplicate wait and timeout, authorization on replay, If-Match mismatch (412), replay-with-stale-If-Match (returns stored result), grant DELETE idempotency (204 on absent, revision increment on present), camera DELETE idempotency (204 on already-deleted, 404 on never-existed), applicable preconditions on absent targets, and a concurrent unrelated request during the duplicate wait (proves non-blocking).

## Validation and revisit

F-1-S4 publishes the OpenAPI update, executable schema tests, focused behavior tests with fakes, and real PostgreSQL transaction/concurrency tests per `tests_rules.md`. The idempotency mechanism is validated by proving: atomic commit of mutation + record, replay fidelity, fingerprint mismatch detection, retention expiration, non-blocking concurrent duplicate wait (with a concurrent unrelated request served within its normal latency budget), and connection pool behavior under a bounded duplicate burst.

Revisit the one-hour retention when a measured client retry pattern exceeds it (e.g., long-running batch operations with multi-hour gaps). Revisit the five-second duplicate wait when PostgreSQL lock contention is observed under load. Revisit the camera-only revision model when a mutation route changes grant state without touching the camera row or its accessible tenant set. Revisit required-key enforcement if a deployment scenario (e.g., internal health-checking tooling) cannot generate UUIDs; an exemption list may be added to the middleware.

## Implementation constraints

The application owns a shared async mutation pool and creates one request-local transaction per operation. Connection, cursor, namespace and pending claim state are never shared between concurrent requests. Default mutation capacity is four connections and four admitted operations; configuration rejects admission exceeding pool capacity. Admission denial and lock timeout return 409. Cancellation and setup failure roll back and release owned resources.

The primary key digest includes an unambiguous serialized tenant, subject and normalized UUID. Expired claims are replaced atomically, and the one-hour retention clock starts when storing the successful result. GET returns grant data and its revision in one database snapshot. Existing repository writers use the same camera scope lock as API transactions. Missing mutation adapters reject writes; there is no weaker direct-write fallback.

Health probes accept optional valid keys; every other API route requires one, including reads. Request-ID resolution and logging wrap correlation/key validation so validation errors remain traceable. Logs use route templates, with an unmatched marker for requests rejected before routing. Weak entity-tags are syntactically accepted but cannot satisfy strong comparison. Camera deletion preserves grants and historical access. Infrastructure validation uses only isolated disposable services and test credentials.
